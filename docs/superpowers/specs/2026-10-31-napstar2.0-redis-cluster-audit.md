## 一句话现状

**这棵树在结构上和已修复的兄弟树一样脆，而且更暴露**：
**16 处裸 `executePipelined`（napstarweb 6 + platform 10）+ 8 处裸 `execute(cb, exposeConnection, pipeline=true)` = 24 处集群不安全的调用点**，
而**全树零集群感知**（grep `RedisClusterConfiguration|RedisClusterHelper|RedisClusterHashPipeline|isCluster` → **0 命中**）。

**但今天的实际风险是 LOW**：这棵树**进不了集群模式** —— 每一个 `oms:` 块都被**整段注释掉**，
**全树没有任何 `RedisConnectionFactory` bean**（工厂来自 Spring Boot 自动装配，只产 standalone/sentinel），
**没有一条代码路径能构造出 `JedisClusterConnection`**。

> ⚠️ **真正的危险在于拓扑在仓库之外**：
> Redis 的生效配置来自 **Nacos**（`node1:18848`，group `NAPSTARWEB_GROUP`），
> **编译期没有任何信号，测试期也没有任何信号**。
> 任何人只要在 Nacos 上设了 `spring.redis.cluster.*`，
> 24 处调用点就会变成**静默丢数据**，而且**应用侧一个错误都不会报**。

### 2.3 为什么这棵树**今天**进不了集群模式 —— 三条独立的证据

**① `oms:` 块全部被注释掉**

```
application/backend/napstarweb/web-controller/src/main/resources/application.yml:108-113
    # oms:
    #   database: 0
    #   hostname: 10.137.220.108
    #   port: 6379
    #   password: sac888
    #   timeout: 5000
```

**已核实，且在构建产物里也核实过**（从 `web-controller-3.0.0.jar` 里 `jar xf` 出
`BOOT-INF/classes/application.yml`，逐字是 `# oms:` / `#   hostname: 10.137.220.108` /
`#   port: 6379` / `#   password: sac888` / `#   timeout: 5000`，行号 **108-113** 一致）。

**② 全树没有 `RedisConnectionFactory` bean**

grep `RedisConnectionFactory` 得到的**全部**命中都是「**注入**一个已有的工厂」或「**实现**一个接口」，
**没有一个是 `@Bean` 造工厂**：

| 文件:行 | 性质 |
|---|---|
| `platform/backend/modelserver/plugins/hisDataSend/.../config/RedisConfig.java:14` | `@Autowired private RedisConnectionFactory factory;` |
| `platform/backend/modelserver/plugins/hisDataProducer/.../config/RedisConfig.java:14` | 同上 |
| `platform/backend/modelserver/plugins/hisDataSend/.../config/RedisMessageConfig.java:25` | `RedisMessageListenerContainer container(RedisConnectionFactory …)` —— 方法参数 |
| `platform/backend/realserver/plugins/rtdata-module/.../RealDataController.java:109` | 字段注入（用来打印工厂类名） |
| `platform/backend/realserver/plugins/rtdata-module/.../OmsWriteByKafkaServiceImpl.java:52,55,58,59` | 字段 / 构造器注入 |

→ **工厂只能来自 Spring Boot 自动装配**（`spring.redis.*`），
而自动装配只产 **standalone / sentinel** → **没有任何代码路径能构造出 `JedisClusterConnection`**。

**③ 内置的 `realserver-oms` 产物没有集群能力**

```
D:\java\apache-maven\mvnRepo\com\sac\platform\realserver-oms\1.0.11\realserver-oms-1.0.11.jar
  → 只有 RedisPipelineUtil.class
  → 没有 RedisClusterHelper
  → 没有 RedisClusterHashPipeline
  → 没有集群可用的 RedisUtilConfig
```

对比本地仓库里更新的 `1.0.14`（兄弟树用的那个）：

```
realserver-oms-1.0.14.jar
  → RedisClusterHelper.class
  → RedisClusterHashPipeline.class (+ 8 个内部类)
  → RedisPipelineUtil.class
```

**已核实（`unzip -l` 实测）。**

> ⛔ **但这三条只是「现在安全」，不是「安全」**。
> Nacos 上的 `spring.redis.*` **不在仓库里**，改它**不需要改任何代码**，
> 也不需要重新编译 —— **改完重启就是集群模式，24 处调用点立刻变成静默丢数据**。

### 3.8 哪些 API 是集群不安全的（SDR 2.7.18 / Jedis 3.6.1 源码核实）

**UNSAFE（会抛）：**

| API | 出处 | 抛什么 |
|---|---|---|
| `JedisClusterConnection.openPipeline()` | `JedisClusterConnection.java:848-850` | `UnsupportedOperationException("Pipeline is currently not supported for JedisClusterConnection.")` |
| `JedisClusterConnection.closePipeline()` | `:856-859` | 同上 |
| `RedisTemplate.executePipelined(RedisCallback, RedisSerializer)` | `RedisTemplate.java:317-337` —— **`openPipeline()` 在 `:320`，`action.doInRedis(connection)` 在 `:323`** | **回调体一次都不跑，一个命令都没发出去** |
| `RedisTemplate.executePipelined(SessionCallback, …)` | `:271-…`，`openPipeline()` 在 `:281` | 同上 |
| ⛔ **`RedisTemplate.execute(cb, exposeConnection, pipeline=true)`** | `RedisTemplate.java:205-235` —— **`connToUse.openPipeline()` 在 `:220`** | 同上（**`execute(cb, true, true)` 这个形态同样炸**） |
| `JedisClusterKeyCommands.scan(ScanOptions)` | `:187-189` | `InvalidDataAccessApiUsageException("Scan is not supported across multiple nodes within a cluster")` |

> ⚠️ **`scan()` 这条命中了本树**：
> `platform/backend/modelserver/plugins/hisDataSend/.../config/RedisPipelineUtil.java:178-193`
> —— `scan(String pattern)` 用 `redisTemplate.execute((RedisCallback<List<String>>) connection -> { … connection.scan(…) … })`。
> 它的 `execute` **不是** pipeline 形态（所以守卫不会报），但 `connection.scan()` 在集群下**照样抛**。
> **这是「守卫管不到的一类集群不安全调用」**，本树里目前只有这一处。

**SAFE（已核实路由行为）：**

| API | 出处 | 说明 |
|---|---|---|
| `RedisTemplate.execute(RedisCallback)` | — | **除非 `pipeline==true`，否则不调 `openPipeline()`** |
| `JedisClusterConnection.hSet / hDel / hGetAll / set / get` | `JedisClusterHashCommands.java:54`、`:260-266`、`:325` | `JedisCluster` **按槽路由** |
| `JedisClusterKeyCommands.del(byte[]...)` | `:85-102` | **跨槽的 key 会被拆开** → **不抛 CROSSSLOT** |
| `JedisClusterKeyCommands.keys(byte[])` | `:153-166` | `executeCommandOnAllNodes` 然后取并集 → **集群安全**（⚠️ 与裸 `JedisCluster.keys()`（`JedisCluster.java:1744-1761`）不同 —— 后者**除非 pattern 含 `{hash-tag}` 否则抛**） |
| `opsForHash().multiGet(key, fields)` | — | 一个 key 上的 `hMGet` → 安全 |
| `opsForValue().multiGet(keys)` | — | 逐 key 路由 → 安全 |

**本树的命令清单里没有任何真正的 CROSSSLOT 多 key 命令**：
全部是 `set`、`get`、`hSet`、`hGet`、`hGetAll`、`hDel`、`lPop`、`rPush`、`del` —— **全是单 key**。
两个「差一点就是」的（`redisTemplate.delete(Collection)`、`opsForHash().multiGet`）**在 SDR 里都是集群安全的**。

> ⚠️ **给要移植集群模式的人的设计约束**：
> 本树所有 `RedisKey` 常量都是**平**的
> （`real_graph:realscope`、`real_graph:data`、`real_graph:symbol:…`，
> 见 `application/backend/napstarweb/common/util/src/main/java/com/sac/application/napstarweb/common/redis/RedisKey.java:33-42`）
> → **不含 `{hash-tag}`** → **hash-tag 分槽方案要改 key 命名约定**。
> **这条对已修复的兄弟树同样成立。**

`tests/validate_java_pipelines.sh`（提交 `1fe06ae`）：

| 2 | 第二种形态的判别器是**实测出来的，不是猜的** | 判别规则：接收者**像**一个 redis template（最后一段标识符含 `redis`，或正好是 `template`）+ **正好 3 个参数** + **第三个是 `true`** + **第一个像**一个 redis 回调。这套规则在四棵树（固定树的 napstarweb/platform + 本树的 napstarweb/platform）上**命中 4 + 8 个真实站点，零误报** —— ⚠️ **napstarweb 里那 16 处 QLExpress 的 `execute(...)` 和 JDBC 的 `stmt.execute(...)` 都没有被误报** |

## 七、处置建议（按「这棵树实际上是什么」排序）

### 7.1 结论：**先不要把兄弟树的做法整体搬过来**

搬不过来，不是因为难，是因为**这棵树没有承载它的结构**：

| # | 障碍 | 为什么不是「复制粘贴」 |
|---|---|---|
| 1 | **没有共享 `oms` 模块**可以安放 `RedisClusterHelper` | `platform/backend/realserver/pom.xml:18-20` 没有 `common/oms`；`platform/backend/pom.xml:25` 的 `common/util` 是注释掉的 → **这是构建图变更**（要么复活 `common/util`，要么新增一个模块） |
| 2 | `RedisUtilConfig` 1.0.14 是**另一套配置契约** | 1.0.14 要 `oms.redisMode`（字符串）+ `oms.clusters` + `oms.sentinels`；这棵树发布的是 `oms.hostname` / `oms.port` → **5 个以上应用的 yml 要重写**，依赖也要升版 |
| 3 | **`RedisKey` 常量没有 hash-tag** | `RedisKey.java:33-42` 全是平 key → **hash-tag 分槽方案要改 key 命名约定**（= 换数据） |

### 7.2 优先级

**① 先让失败「响」，而不是「静」** —— 最便宜、价值最高，**在 standalone 模式下也有价值**：

| 位置 | 改什么 |
|---|---|
| `napstarweb/monitor/.../monitor/services/StartupRunner.java:68` | 不要静默吞掉初始化异常；记 **ERROR + 一个明确的标记**，让「应用起来了但初始化中断了」这件事**可见** |
| `napstarweb/monitor/.../monitor/kafka/RTListener.java:95` | 配一个显式的 `DefaultErrorHandler`，`setAckAfterHandle(false)` 或用 `DeadLetterPublishingRecoverer` → **持续失败不提交 offset**，不静默丢实时数据 |
| `platform/backend/realserver/plugins/rtdata-module/.../kafka/RTListener.java:58`、`:80` | 同上（`INCDATA` / `QUERYRESPONSE` 两个 topic） |

> ⛔ **注意**：**今天在 standalone 模式下，一次瞬时的 Redis 故障就已经会丢数据** ——
> 监听器抛异常 → 默认 handler 重试 9 次 → 跳过并提交 offset。
> **这是一个与「要不要切集群」无关的、活着的缺陷。** ① 这一条**无论切不切集群都该修**。

**② 加一道配置期断言** —— 把「静默损坏」变成「启动失败」：

- 一个最小的 `RedisClusterHelper`（照抄已修复的树的形态：`JedisConnectionFactory.getClusterConfiguration() != null`，
  见已修复的树 `oms/utils/RedisClusterHelper.java:44-63`）
- 加一个 `@PostConstruct`，**发现工厂是集群工厂就 fail 启动**。

**约 30 行。** 需要一个落脚点（三选一）：
`napstarweb/monitor` / 复活后的 `platform/backend/common/util` / 或一个 `realserver-oms` **1.0.15**。

**③ 只有当集群模式真的要上**，按这个顺序移植：

```
napstarweb 的 6 处
  → 8 处 execute(cb, true, true)
    → platform 的 10 处
      → sche-viewer-server 的 15 处
        → scan() 与 KEYS-无-hash-tag 这两个额外风险
```

**用已修复的树的 `isCluster()` 形态**，这样守卫脚本能验证结果
（**但守卫的基线要为这棵树重新定**：napstarweb **6**、platform **10**、sche **15**）。

**④ 别忘了 `backend-gd`** —— 一份逐字拷贝，同样的调用点，**同一个 Nacos group**。
**要么一起修，要么删掉。**

**⑤ 动手前先解决 `realserver-oms` 的版本问题**（见 §八 3）。

### 7.3 代价与风险

| 方案 | 代价 | 风险 |
|---|---|---|
| 什么都不做 | ~0 | **风险无界但概率低**（今天进不了集群；真进了就是 24 处静默丢数据） |
| 建议 ① | **~1 天** | **很低** | 价值高（standalone 模式下也在修一个活着的 bug） |
| 建议 ② | **~1 天** | **低** | 价值高 |
| 完整移植（③） | **~3–5 天** + 一个 `realserver-oms` 1.0.15 + yml 契约变更 + 测试 | **中** |
| 把已修复的树整体搬过来 | **~2–3 周** | **中高** —— 而且它**重复了兄弟树已经做过的工作**，而不是**复用**它 |

## 十二、一句话给下一个人

**这棵树今天进不了集群模式（`oms:` 全注释 + 没有连接工厂 bean），但它的 24 处集群不安全调用点一个都没有守卫，
