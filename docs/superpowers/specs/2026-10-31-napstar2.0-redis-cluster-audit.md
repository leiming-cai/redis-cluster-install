## 一句话现状

**这棵树今天全部是 standalone，集群不安全的调用点一个都没有守卫。**

- **43 处** `executePipelined` 原始命中（口径：**两个会被构建的 reactor**，含被注释掉的）——
  其中 **27 处在带 oms 的应用里**（真能碰到集群路径），**16 处在 `hisDataProducer`/`hisDataSend`**（**没有 oms** → 永远走不到集群路径）。
- 另有 **8 处 `execute(cb, exposeConnection, pipeline=true)`** ＋ **3 处 `connection.scan()`** ——
  同样集群不安全，但**不计入上面那 43**（口径见 §2.2 与 §十 F5）。
- **`isCluster` / `RedisClusterHelper` 在树里出现 0 次** → **全树没有任何守卫**。
- **进不了集群模式，但理由不是「没有代码路径」**：oms 1.0.14 **有**集群分支，是**配置没打开它**——
  `oms.redisMode` 在**所有 Nacos dataId 和所有本地 yml 里都是 0 命中** → `parseMode(null)` → `STANDALONE`。
- ⛔ **生产拓扑是「两个独立单机 Redis」（6379 + 6389），不是集群**（§十 F3）——
  **集群化对这条产品线是一次重构，不是一次配置切换。**
- 🔴 **发现一个真的连错 Redis 的生产缺陷**：`realserver` controller 因为一个**硬编码**的
  `10.137.220.191`（hosts 里 `node1` 是 `10.137.220.201`，**数字转置**），连的是**另一台机器**（§十 F2）。

> ⚠️ **真正的危险在于拓扑在仓库之外**：
> Redis 的生效配置来自 **Nacos**（`node1:18848`），**编译期没有任何信号，测试期也没有任何信号**。
> 任何人只要在 Nacos 上把 `oms.redisMode` 设成 `cluster`，
> 那 27 处 `executePipelined` 调用点就会变成**静默丢数据**，而且**应用侧一个错误都不会报**。

### 2.3 为什么这棵树**今天**进不了集群模式 —— 三条独立的证据（**理由已修订**）

**① 配置侧：`oms.redisMode` 在所有生效配置里都是 0 命中**

生产 Nacos 真值找到了（§十 F1），**所有 dataId 的 `oms:` 块都是老形态**
（`database` / `hostname` / `port` / `password` / `timeout`），**没有 `redisMode`**；
本地 yml 里 `oms:` 块也全是注释掉的（`napstarweb/web-controller/…/application.yml:108-113`）。

→ `parseMode(null)` → `STANDALONE`（基线树 `oms/…/RedisUtilConfig.java:71-74`）。
**集群分支存在，但没有开关打开它。**

**② 能力侧：oms 1.0.14 **有**集群分支（初版说没有，是错的）**

1.0.14 的 `RedisUtilConfig` 有三个嵌套 `@Configuration`：
`RedisClusterConfig`（`:157-193`）、`RedisSentinelConfig`（`:199-257`）、`RedisStandaloneConfig`（`:263-297`），
由 `@ConditionalOnExpression` 按 `oms.redisMode` 三选一（`:158` / `:200` / `:264`）。

→ **「没有代码路径」这句话是错的**。真实理由是 ①。

**③ 产物侧：树里没有任何代码去用它**

`isCluster` / `RedisClusterHelper` 在树里 **0 命中**（§2.1）→
**即使打开了 `oms.redisMode=cluster`，树里的 27 处调用点也一个都不会被守卫**。

> ⛔ **但这三条只是「现在安全」，不是「安全」**。
> Nacos 上的 `oms.*` **不在仓库里**，改它**不需要改任何代码**，
> 也不需要重新编译 —— **改完重启就是集群模式，27 处调用点立刻变成静默丢数据**。

### 7.2 优先级

**⛔ 最高优先级不是集群化，是 §十 F7 那几个还没修的生产缺陷**（尤其是 F2 的连错 Redis）。

| 位置 | 改什么 |

| `napstarweb/monitor/.../monitor/services/StartupRunner.java:68` | 不要静默吞掉初始化异常；记 **ERROR + 一个明确的标记**，让「应用起来了但初始化中断了」这件事**可见** |

**约 30 行。** 需要一个落脚点（三选一）：
`napstarweb/monitor` / 复活后的 `platform/backend/common/util` / 或一个 `realserver-oms` **1.0.15**。

**③ 只有当集群模式真的要上**，按这个顺序移植：


**用已修复的树的 `isCluster()` 形态**，这样守卫脚本能验证结果

**④ 别忘了 `backend-gd`** —— 一份逐字拷贝，同样的调用点，**同一个 Nacos group**。
**要么一起修，要么删掉。**

### F2 —— 🔴 `realserver` controller 连的是**另一台机器**



**`.191` vs `.201` —— 数字转置，是另一台机器。**

```
*** Using Redis Standalone at 10.137.220.191:6379 (connectTimeout=2000ms, readTimeout=5000ms, maxWait=3000ms)
```

**机制（对着 Spring 的解析顺序核实过）：**

1. 现在有**两个** `RedisConfigProperties` bean：
   `omsRedisConfigProperties`（oms 的，绑 `oms:` → `node1:6379`）和
   `redisConfigProperties`（`OmsConfig` 的，**硬编码 `.191`**）。
2. **两个都不是 `@Primary`** → `DefaultListableBeanFactory.determineAutowireCandidate` 落到
   **按参数名匹配**这一步。
3. 而 **oms 的每一个注入点，参数名都literally叫 `redisConfigProperties`**
   （基线树 `oms/…/RedisUtilConfig.java:144`、`:162`、`:181`、`:236`、`:269`）。
4. → **名字就叫 `redisConfigProperties` 的那个 bean 赢** → `omsRedisConfigProperties` **根本没被用上**。

**⛔ Nacos 改不动这个**（它是 Java 里写死的）。
**必须改代码**：删掉 `OmsConfig`，或者把它的 bean 改名成**不再匹配参数名**的。
另外这个应用**还丢了 Nacos 的 `timeout: 5000`**（退回 2000/5000/3000 的默认值）。

## 十三、一句话给下一个人

**这棵树今天进不了集群模式（`oms.redisMode` 在所有 Nacos dataId 和本地 yml 里都是 0 命中），但它的 43 处 `executePipelined` 原始命中（外加 8 处 `execute(cb,…)`、3 处 `scan()`）一个都没有守卫，
而 Redis 拓扑是在 Nacos 上、不在仓库里 —— 改配置不用改代码、不用重新编译，改完重启就是静默丢数据。**

**先修 §十 F7 的 7 个缺陷**，其中 **`realserver` controller 的硬编码 `10.137.220.191`（`OmsConfig.java:22`）是现在就在发生的错**，
而 **`realalarmconsumer` / `transformNapstarModel` 现在就起不来**（Nacos 里没有 `oms:`）。
**再做建议 ①（让失败变响）和 ②（配置期断言）** —— 两者都与「要不要切集群」无关，且在 standalone 模式下就在修一个活着的 bug。
**然后再决定要不要移植兄弟树的做法 —— 但那需要动构建图，不是复制粘贴；
而且生产本来就是两个独立单机 Redis（6379 + 6389），集群化是一次重构。**
**另外别忘了 `backend-gd`（同一个 Nacos group，改一个就是改两个）和 `sche-viewer-server`（这棵树里它是活的部署面，不是休眠代码）。**
