## 七、DDL 来源 —— **`sac` / `cmt` / `hds` 是第三方系统的表，本项目只有读权限**

> 📌 **用户 2026-11-03 明确**：`cmt`、`sac`、`hds` 是**第三方系统表**，
> 该项目**有读取权限**。
> ⇒ **不是本项目的表，本项目也不该去建它们。**
> 这一条把 D10 的性质整个改了（见下）。

### 7.1 只读是**实测确认**的，不是推测

| schema | select | insert | update | delete |
|---|---|---|---|---|
| `sac` | 32 | **0** | **0** | **0** |
| `cmt` | 12 | **0** | **0** | **0** |
| `hds` | 1160 | **0** | **0** | **0** |
| **`info`（本项目自有）** | 0 | **4** | 0 | 0 |

（华盾交付树，mapper XML 口径；基线树同形。Java 代码里对这三个 schema 也**零** DDL/DML。）

⇒ 读写边界清楚：**读第三方、写自己**。

### 7.2 活库的权限模型印证了这一点

```
 schema | owner |            acl
--------+-------+-----------------------------
 cmt    | cmt   | {cmt=UC/cmt, info=U/cmt, sac=U/cmt, hds=U/cmt}
 hds    | hds   | {hds=UC/hds, info=U/hds, cmt=U/hds, sac=U/hds}
 info   | info  | {info=UC/info, cmt=U/info, sac=U/info, hds=U/info}
 sac    | sac   | {sac=UC/sac, info=U/sac, cmt=U/sac, hds=U/sac}
```

- `UC` = USAGE + CREATE（owner 自己）；`U` = **只有 USAGE**（能看见对象名，**不能读表**）。
- 跨 schema **只授 USAGE** ⇒ **表级 SELECT 权限由建表的第三方单独授予**。
- 表级权限现状：`info` 的 30 张表上，`info` 角色有全 7 种权限（SELECT/INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER），
  **其它三个 schema 一张表都没有**（所以连表级权限行都不存在）。
- `initPostgresDB.sql` 建了 **4 角色 + 4 schema**（`info`/`cmt`/`sac`/`hds`），但**只给 `info` 建表**。

### 7.3 本项目负责哪部分

| 域 | 谁建表 | 装在哪 | 现状 |
|---|---|---|---|
| `info`（30 表） | **本项目** | `/pkg/database/postgresql_install/sqls/info/InitTable/*.sql`（PG 方言） | ✅ 已装，活库 30 表 |
| `sac` / `cmt` / `hds` | **第三方系统** | 不在本项目安装包内 | 本环境 0 表 |

### 7.4 ⇒ D10 的性质变了

**原表述**：「三个 schema 缺 DDL → 挡住 `transformNapstarModel` → 要把 `SystemTable.sql`
从 MySQL 转成 PG」⇒ **方向错了**。

**实测后的正确表述**：
- `transformNapstarModel` 是**读** sac/cmt、**写** info 的**转换作业**
  （`SacDataSourceConfig` / `CmtDataSourceConfig` / `InfoDataSourceConfig` 三段数据源；
  `transnapstardata-dao` 的 `DataBaseMapper`/`OtypeMapper`/`WiringMapper` 读 sac，
  `WiringMapper` 写 info 2 处）。
- 它要的是**第三方库里有数据**，**不是**本项目去建表。
- ⇒ **真正的阻塞是「本环境没有第三方数据」**（第三方系统没接进来），不是「缺 DDL」。
- ⇒ D10 从 🔴 降为 🟡：**不是代码缺陷，是环境/依赖缺口**。

### 7.5 顺带查清的事实（供找第三方时用）

- 平台上唯一像 `sac` 源的是 `mysql_install/SystemTable.sql`
  （154 行 / 15 表，`engine = innodb` ×15、`smallint(5)` ×14），
  建的表 `AttributeTypes` / `ObjectTypes` / `Choice` / `Wiring` 等
  **正好对得上** mapper 里的 `sac.attributetypes` / `sac.objecttypes` / `sac.choice` / `sac.wiring`
  ⇒ 它大概率就是 `sac` 在 **MySQL 布局**下的建表脚本。
  ⚠️ 但**没有任何脚本执行它**（`mysql_server_info_init.sh` 只跑 `info` 的那 6 个脚本）
  ⇒ **孤儿文件** —— 要用得先问第三方。
- `hds.*`（`h_daymvpointstat_` / `h_daylinestat_` / `h_cycle_*_day_` / `h_hour*_stat_` 等，
  mapper 引用 1160 次）**在安装包里完全没有建表脚本**；
  `CreatehistoryTable.sql` 只建 `H_AlarmEvents` / `H_DataEdits` / `H_TempId` / `H_TimeStamp`
  （**表名形态完全不同**，不是 hds 那批）。
- `cmt.commitlist` 同样**无建表脚本**。
- `hds` 的表名形态（`h_day*` / `h_hour*` / `h_cycle_*` / `hmonth_`）= **统计/历史产物**
  ⇒ 由**采集侧**产出，不是本项目建的。

### 7.6 一句话给下一轮

> **别去建 `sac` / `cmt` / `hds` 的表。**
> 本项目只读它们；表由第三方系统建、由第三方授 SELECT 权限。
> 要让 `transformNapstarModel` 能跑，要的是**把第三方数据接进来**（接第三方库，
> 或拿第三方的 PG 建表脚本 + 授权），**不是**在本项目里补 DDL。

## 八、门户树（集控-IV区门户）的特殊性

- **有 git**：`application\.git` + 3 个 worktree
  （`fbx-unit-auto-detect-execution` / `placed-models-mode-buttons` / `scene-editor-split`）
- 独有模块：`platform/backend/portal`（59 java）、`platform/backend/processsinfomodel`（3）、
  `application/backend/smartoptsys`（39）、`application/backend/3dmanager`
- 独有前端：`application/frontend/{3d-manager, 3d-sdk, smartoptsys, mobileapp, napstarweb}`
- ⚠️ **`3dmanager` 的 flyway 迁移是 MySQL 方言**
  （`AUTO_INCREMENT`×4 / `COMMENT`×44 / `TINYINT|DATETIME`×10 / `ON UPDATE CURRENT_TIMESTAMP`×2），
  而门户库 `cpspg` 是 **PostgreSQL**（实测只有 `info` schema / 36 表，无 `3dmanager%` 表）。
  ⇒ **门户线自己的 3dmanager 迁移脚本在 PG 上跑不起来**（跟华盾无关的独立问题）。
- 门户产物版本是 `2.0.2`（`portal-controller-2.0.2.jar`），与 mvnRepo 的 `2.0.0`/`2.0.2` 对得上。
